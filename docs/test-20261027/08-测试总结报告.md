## 一、结论

**这套系统整体可用，没发现致命问题（S1 = 0），但还不能说「放心用」。**

三条理由：

1. **最关键的承诺守住了**：每个用户的空间互相看不见——我用 28 条越权用例打它（读/改/删/附件/回收站/版本/导出/搜索逐字探测），**全部 404，且与「不存在的 id」响应逐字一致**，连存在性都不泄露。这是这个系统最有价值的一处实现。
2. **但有三处会实际伤到用户**：导入不校验也不原子（1KB 空文件就能落一条空笔记；2001 条目的包提示「已拒绝」却写进 2000 条）；界面**根本无法修改笔记标题**（所有笔记永远叫「未命名笔记」）；搜索会因库里存在 1–2MB 的正文笔记而慢 4 倍，并发下 P95 达 14 秒。
3. **文档债很重**：8 个可达接口没登记、参数表漏了 20 个键、测试规模有 4 个互相矛盾的数字。任何人接手都会踩坑。

**准确表述**：一个核心安全做得扎实、功能实现大体正确、但在「导入原子性 / 标题编辑 / 搜索性能」三处有明显缺口、文档严重滞后的个人知识库。

## 三、必须先处理的 5 条（S2）

1. **导入不校验也不原子**（DEF-E2-001）：空文件落空笔记；2001 条目 ZIP 说「已拒绝」却写入 2000 条。任何登录用户可用 1KB 文件污染自己的库。
2. **界面无法修改笔记标题**（DEF-E4-001）：API 支持 PATCH title，但前端没有任何入口，新建时写死「未命名笔记」——用户实际上没法给笔记起名。
3. **大正文拖慢全局搜索**（DEF-E3-001）：库里有 1–2MB 正文时，同一查询 291ms → 1165ms，删掉即回落。
4. **并发下搜索塌陷**（DEF-E3-002）：10/25/50 并发 P95 3.6s / 8.2s / 14.4s，吞吐恒定 ~15 rps 不随并发增长。
5. **8 个可达接口未登记在契约里**（DEF-E5-002）：其中 4 个是会触发外连的 POST /run，而 `enabled=false` 拦不住它们（DEF-E5-009）。

## 四、值得肯定的部分

1. **空间隔离做得比多数同类系统都好**：越权响应与「不存在」响应逐字一致，这是主动设计过的痕迹。
2. **中文检索是真的能用**：1 字「天」、2 字「天气」（短语精确，不误命中只含「天」的笔记）、3 字都命中；改正文后索引同步正确。这是产品最大卖点，实至名归。
3. **SQLite 用法干净**：三档并发 1860 请求 **0 次 database is locked**，同笔记 10/20 并发写零丢版本，WAL 峰值仅 0.09MB。
4. **版本模型正确**：快照数 = version−1，回滚产生新版本且不丢当前内容。
5. **上传防护扎实**：MIME 白名单 + 服务端重命名 + 路径穿越清洗 + SVG 强制下载 + nosniff。
6. **既有测试全绿**（328/328），说明工程底子不差。

## 八、方法论层面留下的两条

1. **既有测试全绿不等于质量好**：328 个 Java 测试零失败，新增黑盒用例 5.5% 失败。差别在于既有测试覆盖的是「实现自己」，新增用例覆盖的是「用户会怎么用、攻击者会怎么打」。
2. **子代理的结论必须复验**：这次 5 条关键主张里，1 条（同名笔记静默丢链）复验后**不成立**，被我降级并改写。如果不复验，就会把一条不实的 S2 交给开发，既浪费工时也损伤测试报告的可信度。
